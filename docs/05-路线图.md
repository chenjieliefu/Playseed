# Playseed 路线图

路线按能力风险排序，不按示例游戏数量排序。每个阶段完成后再扩大范围。

## 两条交付方向的产品框架（0.8.39 起）

产品不按技术栈分成两个产品，而是按用户听得懂的问题组织：先问“朋友怎么玩到”（下载到电脑玩 / 发链接在网页直接玩 / 还没想好），再结合画面维度（平面/立体）进入四条制作路径：

| 画面 | 本机（下载到电脑玩） | 网页（发链接即玩） |
|---|---|---|
| 平面 2D | 已稳定（P0 验收范围） | 0.8.40：网页画板制作与本机浏览器闭环；公开托管未接 |
| 立体 3D | 实验性：GPT + Godot 房间寻物；Blender 按需供模型 | 0.8.40：实验性Three.js网页制作与本机浏览器闭环 |

两条方向共用对话、方案、素材与版本前厅；图片/声音/GLB 素材中立共用，Blender 永远只服务素材层。界面只问“怎么玩到”和画面维度，不把引擎暴露给用户。当前“玩的方式”期望（`delivery`）已可记录并按项目保存；0.8.40网页两格已接通本机浏览器制作流程，公开分享链接仍未接通。

## P0：提高小型 2D 游戏的成功率

目标：让不同类型的明确方案都能较稳定地产生第一版，并能连续修改三轮。

交付：

- 建立平台跳跃、俯视射击、经营、解谜、塔防或轻度 RPG 的固定验收样本。
- 将每个样本拆成操作、核心循环、胜负、重开和三轮修改检查。
- 改进生成规则和自动修复，使失败原因对用户清楚可见。
- 记录首次制作成功率、修改成功率和旧功能回归率。

完成标准：至少五种玩法各有一个独立规则的可玩样本；每种连续修改三轮时，原有核心需求不丢失；失败不会覆盖上一版。

当前进度：0.8.6 已加入自动操作探针，修通 macOS 原生文件选择，并整理首页输入区。平台跳跃、俯视射击、经营、解谜和塔防的五类固定方案及每类三轮修改任务已经写入统一验收矩阵；验收脚本会把结果隔离保存，避免污染用户项目。2026-09-06 五类第一版真实生成最终 5/5 通过，其中平台跳跃经过一次自动修复，其余四类一次通过。五类三轮修改现已完成，15/15 通过运行检查、旧操作探针和样本专项玩法检查，未触发自动修复，旧版文件保持不变。具体检查范围见当前能力文档；随后完成五款自动输入通关、四款失败路径与重开检查，并核对结算画面。射击结束状态报错和两款文字交叠已修正。普通用户体验和更大样本的稳定性仍未完成。

## P1：完成视觉素材链路

目标：用户提供或生成的角色、场景和界面素材真正进入游戏，画面风格保持一致。

交付：

- 接入图片视觉理解，让模型知道上传图片画的是什么、适合做什么。
- 接入角色和场景图片生成，并保存生成提示、尺寸、用途和来源。
- 支持角色切图、基础动画帧、背景分层和常用界面组件。
- 让右侧素材、动画、特效工具可以配置后通过对话加入游戏。
- 增加画面越界、文字遮挡、缺图和素材未使用检查。

完成标准：从用户参考图或平台生成素材出发，完成一个视觉风格统一的 2D 游戏；素材可以替换并形成新版本。

## P2：增加玩法深度和声音

目标：从一次性小循环扩展到有递进、有反馈的短游戏。

交付：

- 多关卡或波次、敌人行为、技能、升级、资源取舍和难度曲线。
- 音效、背景音乐和音量控制；记录素材授权和来源。
- 将玩法、画面、声音和操作反馈分项验收。

完成标准：一个新用户可以连续玩 10 至 15 分钟，理解目标，感受到难度递进，并能指出每轮修改带来的变化。

## P3：验证小规模 3D

目标：接通第一个真正的 3D 垂直样本，不把 3D 需求转成 2D。

交付：

- 从低多边形小房间或小岛开始。
- 接入模型、材质、第三人称或第一人称相机、碰撞、交互和基础动画。
- 增加穿模、相机、碰撞、光照和性能检查。
- 为 3D 生成定义新的工程结构，避免沿用单一 `game.gd` 的限制。

完成标准：用户能通过对话制作一个可走动、可互动、有明确目标和完成状态的小型 3D 游戏，并在目标 Mac 上稳定运行。

## P4：分享和发布

目标：创作者能把游戏交给别人直接玩。

交付：

- 网页方向：生成分享链接，未安装 Playseed 的浏览器用户可直接打开并完成一轮（依赖网页两格先接通）。
- 本机方向：保持完整源工程导出，再评估独立包（macOS）作为补充。
- 自动检查导出产物、启动、资源完整性和基础设备尺寸。
- 生成分享文件或链接，并保留对应源版本。

完成标准：未安装 Playseed 的测试用户可以打开游戏并完成一轮。

## P5：云端和多人产品化

目标：从单机原型变成多用户服务。

交付：账户、云端项目、对象存储、任务队列、执行隔离、额度和费用控制、监控、恢复、团队协作与发布治理。

完成标准：不同用户的数据和运行环境相互隔离，任务可恢复，费用可统计，核心创作流程不依赖开发者电脑。

## 当前下一步

2026-09-08（0.8.53，最新）：用户已认可元素守望第17版目前可用，明确返回平台完善。展示游戏暂告一段落，不再默认扩充技能和美术。首批平台工作补网页连续修改上下文、自动修复时保留素材附件与既有要求、运行组件能力说明，以及如实的版本检查记录。已用独立2D/3D固定响应夹具走正式制作、三次修改和恢复；0.8.53继续加入正式暂停/继续及两次重玩检查，失败阻止新版本保存并进入原有修复。这验证编排及基础操作，不是全部机制回归或新一轮真实GPT生成成功率。

第一阶段可用版按以下优先级继续：

| 优先级 | 平台要补的结果 | 验收标准 |
|---|---|---|
| 1 | 不同想法都能连续制作 | 新的2D/3D想法分别生成，再连续修改；记录成功率、等待时间和失败恢复，避免只验证同一示例 |
| 2 | 素材单项可管理、可替换 | 区分导入、AI图片、程序组件；明确角色/背景/技能被哪一版引用；单项重做、采用、恢复不会改坏其它部分 |
| 3 | 用户能把作品交给朋友 | 本机试玩与公开链接清楚区分；网页托管、更新、撤回和访问失败提示；随后完善本机玩家安装包 |
| 4 | 不需要开发者陪同安装 | 依赖检查、账号接入、文件夹/系统权限说明、迁移与备份；新电脑不依赖开发机绝对路径 |
| 5 | 过程和费用可理解 | 阶段状态、取消/重试、失败原因、每轮用量与预算控制；不能用进度动画代替实际完成 |

多模型供应商接入放在素材身份与替换关系稳定之后。对外发布前还需陌生用户独立完成测试、运行与素材边界复核；本机样例可玩不等于平台已适合公开发行。以下为历史节点。

### 基础素材阶段历史进展

P0 固定样本验证已完成。P1 已接通参考图片理解，以及单张图片生成、预览、采用入库和来源记录。当前通过“生成图片：描述”及聊天引导按钮开始，每次一张；不会自动生成整套方案素材。实现位于 `image_assets.py`，输入与游戏应用仍走 `resources.py`、`creator.py`、`producer.py`。

0.8.16已将方案现有素材条目接入对话引导，支持逐项选择、带画风预填生成请求和原生上传。0.8.17已支持用户为方案条目手动关联已入库图片，记录方案版本和用途，后续模型请求携带关联。0.8.18已将任务上传和生成后采用直接接入任务关联。0.8.19已接通复合条目拆分建议、用户确认和子任务准备，真实验证了角色与背景分项。一套新生成角色与背景已完成采用、关联和真实入场验证，边界遮挡通过正常修改流程修正，结果见当前能力文档。0.8.20已接通可选择的画风参考和来源记录。真实蘑菇样本出现不透明棋盘格底，未采用；0.8.21已完成透明像素检查、可审阅修复入口与不透明修复结果拒绝采用。0.8.22另接macOS本机主体分离，真实蘑菇已获得透明稿并在隔离样本采用，支持收边和深浅底预览；仍存在局部浅色残留。0.8.23继续打磨素材细节，补上显式浅色残边清理、透明原稿保护及前后对照，验收见[素材质量标准](08-素材质量标准.md)。0.8.24已补合成白色主体、细线和独立小主体的误删保护验证。真实白色长毛样本未通过，已隔离并保留限制。0.8.25已完成规则切图、帧动画预览与真实游戏修改/恢复验收，0.8.26已补可选底部对齐并经真实第6版验证；后续补充了界面图片、源工程导出和恢复专项；帧间轮廓和画风一致性作为进阶项保留。不要扩大3D范围，不要把单张成功当作完整美术生产线完成。

### 用户追加的3D素材实验（0.8.10）

按用户明确要求优先完成浏览器预览及项目模型入库，未提前宣布P3游戏制作完成。后续P3接入时先补齐模型命名、用途、直接重新预览与来源记录，再将符合条件的模型用于独立Godot3D样本；该样本须另建相机、碰撞、交互与重开验收。2D素材任务分解仍在P1待办中。

### 素材生产优先方向（用户2026-09-07追加）

用户需要管理游戏中的独立组成部分，而不是理解一组零散制作工具。下一步把角色及其状态、背景、道具组织成稳定素材条目：名称、用途、来源、图片/模型版本、当前游戏引用关系；例如小鸟普通/受伤状态、小猪、背景、木桩、弹弓。单项重做应只生成该项的候选版本，预览采用后替换对应引用，经游戏检查生成新版，允许恢复。不能把程序绘制画面直接宣称为已生成图片。0.8.38只完成已有图片的来源分类与单张重新设计入口，整套自动拆分和稳定替换关系仍待实施。

后续按能力接入多模型：游戏需求与美术约束 → 角色/场景设计稿与状态图 → 2D直接制作图片素材，3D按需要制作模型 → Godot组装玩法与验证。图片、视频和建模工具按各自输入输出与验收结果接入；用户提及Seedance、Nano Banana作为候选，尚未完成能力核实、账号接入或生产验证。GPT负责规划与编排，Three.js负责适合的三维预览/交互，Blender负责模型制作；不要求所有游戏依次经过所有工具。

先完成单项素材身份、版本和引用关系，再扩展供应商；不同供应商结果复用同一预览、采用、来源、费用提示、失败恢复和游戏验收流程。
