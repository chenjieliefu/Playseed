# 关键决策记录

这里记录会影响多个模块的长期决定。新决定追加编号；如果推翻旧决定，保留原记录并标明替代关系。

## D001：Playseed 是产品，Godot 是底层引擎

- 状态：生效
- 决定：Playseed 使用 Godot 提供渲染、输入、场景和运行能力，但品牌、界面、创作流程和产品逻辑由 Playseed 自己定义。
- 原因：避免把产品做成 Godot 编辑器换皮，也避免重复实现成熟的游戏运行基础。

## D002：GPT、Godot 和 Python 分工

- 状态：生效
- 决定：GPT 负责理解与生成 GDScript；Godot 负责实际运行游戏；Python 负责编排、校验、隔离和版本保存。
- 原因：模型输出需要真实引擎验证；引擎无法独立理解自然语言产品需求；编排层需要保护文件和版本一致性。

## D003：小型 2D 优先，3D 是独立阶段

- 状态：生效
- 决定：先提高小型 2D 的生成与连续修改成功率，再用新的工程结构验证 3D。
- 原因：Godot 支持 3D，但 Playseed 当前单脚本生成、素材和检查能力不足以可靠制作 3D。

## D004：方案、游戏和版本是不同对象

- 状态：生效
- 决定：确认方案不会自动宣称游戏完成；候选游戏只有检查通过后才能成为新版本；恢复旧版也生成新版本。
- 原因：让界面状态可验证，并保证失败时可以恢复。

## D005：每个游戏使用用户选择的独立文件夹

- 状态：生效
- 决定：新项目绑定一个空文件夹。游戏、素材和版本存在其中；本机 `.playseed/` 保存对话方案和任务日志。
- 原因：让用户知道游戏在哪里，并支持整个项目移动、重命名和删除。

## D006：生成代码只在隔离进程中运行

- 状态：生效
- 决定：Playseed 创作界面不直接加载生成代码。解析、预览和试玩都通过受限 Godot 子进程完成。
- 原因：模型生成代码不可信，需要限制网络、进程和文件访问，避免破坏创作应用与本机数据。

## D007：一个聊天框贯穿创作

- 状态：生效
- 决定：首页用于输入第一句话；进入项目后在同一个聊天框完成澄清、方案修改、制作和试玩反馈。右侧工具负责查看和补充，不承担主流程。
- 原因：目标用户不应先理解专业编辑器和工作模式。

## D008：Three.js 首先作为独立素材工具接入

- 状态：0.8.9实验入口已实现。
- 决定：由素材区与聊天打开本地浏览器预览，先验证简单参数模型和GLB导入导出，继续使用Godot运行游戏。
- 原因：Godot界面不直接执行浏览器JavaScript；先明确工具边界，不把引擎可支持3D误报为平台已经实现3D游戏。

## D009：声音按版本保存，试玩音量不改写版本

- 状态：生效（0.8.31）。
- 决定：声音独立入库，制作时将文件、来源与默认音量复制到版本；恢复使用旧版快照。试玩时调音量只影响当前窗口，重开保留，退出不写回版本或项目默认值。
- 原因：如果版本直接引用可变素材库，改音量或导入新声音会改变历史游戏。额外复制会占用空间，但保证恢复与导出可复现。声音与图片附件隔离，避免把声音元数据当作模型听过音频的证明。
- 播放依据：Godot的[AudioStreamWAV](https://docs.godotengine.org/en/stable/classes/class_audiostreamwav.html)提供PCM数据与循环边界，[AudioStreamPlayer](https://docs.godotengine.org/en/stable/classes/class_audiostreamplayer.html)负责实际播放、暂停和音量。可信宿主封装文件访问，生成代码只使用声音编号。

## D010：首个3D范围采用场景数据和可信运行器

- 状态：生效（0.8.32）。
- 决定：3D房间寻物使用独立格式，AI输出有界的布局与目标数据，宿主提供角色、碰撞、相机和交互；每版保存数据与运行脚本快照。
- 原因：直接扩宽2D脚本生成会同时引入任意场景结构、相机和物理风险。先用可达性校验加真实输入检查，能把这些责任分开；代价是只能表达明确的小范围机制，不能承诺自由3D创作。
- 后果：不支持的核心玩法直接说明限制，不变成同一种寻物游戏。已有2D/3D项目不直接转换；旧版恢复保留旧运行行为。GLB、动画和新的机制需要扩展格式、独立验收，再扩大入口范围。


## D011：模型视觉与碰撞外盒分离，采用时保存原文件

- 状态：生效（0.8.33）。
- 决定：首批GLB只替换静态障碍外观。宿主提取网格并等比贴地，独立盒形承担碰撞，薄底座显示范围；采用的文件和来源随版本保存。
- 原因：模型的镂空、细枝与凹形不能直接等同于可行走空间。保留明确外盒可复用布局可达性与真实物理检查；代价是不能穿过模型镂空处。快照避免素材库改名或来源更新改变旧版本。
- 后果：贴图、骨骼与复杂碰撞不自动纳入；导入成功和看过预览不等于游戏采用，必须经过新版本检查。


## D012：Blender只执行可信造型脚本，先草稿后采用

- 状态：生效（0.8.34）。
- 决定：AI输出有界部件数据，隔离Blender执行仓库固定脚本。GLB、blend、描述与双角度图片保存为独立草稿；人工检查后才能入库，入场另建游戏版本。
- 原因：让模型直接提供任意Python会扩大本机执行权限，也难以约束形状与资源开销。有界数据可重复验证，代价是只能组合基础形状，不能承诺精细建模。
- 后果：文件有效和碰撞检查通过都不等于造型合格。对明显分离部件增加拒绝，仍保留人工审阅、放弃和改描述重做；不会自动反复消耗额度修图或制作整套模型。

## D013：两种交付方式一条产品线，先问“怎么玩到”再制作

- 状态：生效（0.8.39）。
- 决定：产品不按技术栈拆成两个产品，而是先问用户“想让朋友怎么玩到”——下载到电脑玩（本机），还是发链接在网页直接玩（网页），还没想好也可以先开始；结合画面维度形成四条制作路径：本机 2D（GPT+Godot，稳定）、本机 3D（GPT+Godot 房间寻物，实验）、网页 2D（GPT 生成自包含网页，浏览器画板，建设中）、网页 3D（GPT+Three.js，建设中）。创作主页询问并记录“玩的方式”期望（`delivery`：native/web/未定）到项目；网页两格接通前如实显示为尚未接通，先做本机可试玩版本，不提供假装可用的入口。
- 原因：网页游戏用 GPT 加浏览器本身即可交付，不需要 GDScript 与 Godot 桥接成本；而“真正能下载安装的游戏”需要本地引擎（当前为 Godot），精细模型按需由 Blender 提供。两类用户需求真实存在，但玩法生成与验证层不应长期双轨并行；两条方向共用对话、方案、素材与版本前厅，素材（PNG/WAV/GLB）中立共用，Blender 永远只服务素材层。先共用前厅并分别隔离验证，等网页方向成熟后再评估是否独立成产品。
- 后果：网页 2D 不依赖 Three.js，Three.js 只服务网页 3D；界面只问用户听得懂的话，不把引擎选择暴露给用户；`delivery` 是创建时的期望记录，不构成能力承诺；本机制作不受网页期望影响。


## D014：网页生成模块由可信浏览器宿主管理

- 状态：生效（0.8.40），更新D013中网页制作未接通的阶段结论。
- 决定：2D使用浏览器画板，3D使用本地固定Three.js；AI仅输出玩法模块，宿主提供输入、画布、图片和主循环。两种交付共用前厅与版本，已生成项目保持原格式，网页不经过Godot解析。
- 验证：网页模块先做JavaScript静态检查，再在独立Chromium沙箱中检查启动、真实鼠标/键盘状态变化和重开，通过后提交新版本。浏览器无用户登录信息，服务只读且限制到本版本，阻止外部请求和弹窗。静态检查不是安全边界，隔离细节与限制见[系统架构](03-系统架构.md)。
- 后果：先支持程序几何体和PNG，音频、GLB、摄像头手势和公开托管未接通；本机浏览器试玩不等于可公开分享。额外依赖Node、Chrome和网页检查组件。
